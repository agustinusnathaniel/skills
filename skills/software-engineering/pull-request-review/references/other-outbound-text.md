# Other Outbound Text

Rules for text the user sends outside a code review. The voice, link, and
approval rules in the main skill apply here too.

## Before drafting

- Check whether the thing is already done. Read the user's own recent posts,
  commits, and thread replies; if they already posted, read what they actually
  sent, since they revise drafts.
- Do the checks a thread will ask about before opening it.

## Team chat and issue threads

- Keep the post short. Detail goes in a thread reply, the PR body, or a doc.
- Put a proposed solution in a reply, not in the opening post.
- Make a post self-contained when it leaves the immediate team.
- For teams spread across timezones, offer written context with a suggested
  reading order rather than a call.
- When editing the user's own draft, keep their points. Cut only unsourced or
  easily challenged claims, unasked-for lecturing, and mentions that add
  pressure; never shrink it to a safe one-liner.
- Re-read every sentence for a second meaning before handing it over.
- When a fact changes, update every related draft in the same turn, such as
  a PR body and its announcement.

## Support and customer replies

- List the customer's exact questions, their deadline, and what others have
  already promised them, and answer each question.
- Verify every claim against the code before stating it. Make no promise the
  user has not confirmed.
- Phrase actions so they stay true after sending: "I'm passing this to the
  team", not "I've passed this".
- Use wording that keeps the door open ("not for now" over "no").
- Flag any destructive step and offer the safe path first.
- Leave out the names of sub-processors and vendors.

## Status updates

- Match the shape of the user's last posted update.
- Report outcomes, not agent mechanics. Leave out routine chores.
- Name no people; link every item in full.
- State nothing as fact without a source, and keep private items out of the
  posted text.
